# Phase 29 decisions: clients (phase 29)

- **A client is kept by the app, in `storage`, and the daemon never learns of it.** Key `flightdeck.clients`, shape `{ v: 1, clients, overrides }`, read with a schema that fills what an older value lacks (a client without `defaults`) and ignores fields it does not know, so later areas can add fields without a migration. A missing, unreadable or foreign value reads as an empty list and is not rewritten until the person changes something. The only wire change is the optional `Project.projectKey`.
- **Client names are unique, ignoring case.** The switcher shows names only, so two clients with one name would be indistinguishable; `add` and `rename` refuse a blank or taken name and say nothing else.
- **Deleting a client drops the overrides that pinned a project to it, not the pins to Unassigned.** Its projects are then judged by the other clients' rules again, so they land in another client or in Unassigned. No session, cost, budget or card is touched.
- **A folder rule's host is the host id, not its name.** Names are typed by the person and may repeat; ids are what sessions and rows carry. The rule form picks the host from a list that shows names. A rule whose host id is no longer a known host (removed or paired again) matches nothing, since no row of a known host carries that id, and the Clients screen shows it as "unknown host" so it can be fixed or deleted. It never fails.
- **The unit of a rule is the project key; a folder rule needs a folder.** A remote-keyed project has no path in its key, so the folders its sessions ran in (`knownProjects`, from the session rows the app already loads) stand for it, and a project with no row and no folder in its key can only be claimed by a remote rule or an override. Each folder is judged alone: two folders of one project that belong to two clients are a conflict, the first client in order wins, and the others are listed so the screen can flag it. Two rules of different clients on the same key are not a conflict: order decides, on purpose, so a specific rule can sit before a broad one.
- **A remote rule never claims a folder key.** A key that starts `host:` has no remote, so even `*` does not match it. `*` is only a trailing wildcard (a prefix); anything else is the whole remote, compared in lowercase.
- **"Suggest from what I have" takes the owner as the first path segment after the host.** `github.com/acme/api` offers `acme` with `github.com/acme/*`; Azure DevOps over https is the same (`dev.azure.com/orgb/*`), and over ssh the `v3` segment is skipped (`ssh.dev.azure.com/v3/orgc/*`). A project already claimed by a rule or an override, including one pinned to Unassigned on purpose, is not offered again; a client that already has the owner's name gets the rule instead of a duplicate. Other hosts that put more levels before the owner are not special-cased.
- **`Project.projectKey` is left out, not guessed, when the daemon has no project keys.** The budget path falls back to the folder, but a bare folder is not a key the app could place in a client.
- **The project key is asked on the asynchronous path, never `keyFor`.** `keyFor` spawns `git` synchronously and blocks the event loop (it is what timed out `uso.test` on Windows). `project.list`, `project.add` and `project.update` answer through `Board.withKey`, which awaits `ProjectKeys.resolve` (cached per folder, one in-flight ask per folder); a list asks all its projects together. A test makes `keyFor` throw to prove the request path never calls it.
- **What the selection filters, screen by screen.** Sessions: the rows, by their project key. Board and Workflows: the project picker of a host (`projects` route with `focus`); the host's own Projects screen (add, edit, remove) is host administration and always lists every project, so a project is never out of reach. Conversations: a message shows when **either** of its two sessions is in the selection (a message between two clients shows under both), and a message whose sessions the app cannot place counts as Unassigned. Budgets: the host's own budgets always show (they cap everything on the host), a project budget shows with its client, and a line says how many are hidden. "Needs you", the tray, the notifications and budget alerts take no selection at all, and a test sends a request in one client's project while another is selected.
- **The store knows the clients.** `store.clients` is the model, `state.clientList`, `state.clientOverrides` and `state.clientSelection` are what the screens read, and `store.clientScope()` (memoized per state) resolves a project key to a client from the session rows and the hosts' projects the app has loaded. A selection that names a client that is gone falls back to all clients, in storage too; with no client defined every selection is all. A Board picker that loads a host's projects hands them to the store (`rememberProjects`), the same list the palette keeps.
- **A folder key is named after the daemon's host, not the app's host id.** `host:<hostName>:<folder>` carries the name the daemon has for itself, while a rule keeps the app's host id. The scope maps a folder key's name to the host id through the host's name and the name its `hostInfo` reports, so a host-scoped folder rule claims a project known only by its key; a name no host answers to is simply not matched.
- **With no client defined only Settings changes.** The Clients screen is reached from the switcher (shown once a client exists), from the palette ("Manage clients", always there so the first client can be made) and from one line in Settings. A sidebar item would change every print for a person who never uses clients, so there is none; the only screen that differs with no client is Settings, which gains that one line (the maintainer's call, 2026-11-01).
- **The switcher, the chips and Assign.** The switcher is a menu in the sidebar (all clients, each client with its busy sessions, Unassigned with its project count, Manage). A mark beside it counts the requests waiting in a client other than the selected one; it is a count of the same items "Needs you" already lists, never a filter of them. A project header wears its client's chip only while all clients are shown, and a request in "Needs you" always does. A project with no client offers Assign: pin it to a client by hand, or make a rule from its owner (a new client, or a rule added to the client that already has the owner's name). A request whose session the app cannot place counts as Unassigned.
- **The switch shortcut.** `Alt+Shift+C` (in the app only, like Ctrl+K) walks all clients, each client in order, Unassigned, then all again, through `AppStore.nextClient`; it does nothing while no client exists. Ctrl+Shift+C was avoided because browsers use it for the inspector, Ctrl+Alt+K because Ctrl+K is the search.
- **Axe, themes and languages for the Clients screens** are checked by `demo:shots` (the four client prints are shot in both themes and both languages, each with axe), not by unit tests, because axe needs a real layout. The vault group of secrets with no client reads "Not tied to a client" (pt-BR "Sem vínculo com cliente"), as the spec words it.
- **Clients move between desktops as text.** Export shows the JSON in a read-only box to copy, and Import takes pasted text and merges by client id (new ids added, the same id replaced, nothing deleted, overrides to a client that does not exist dropped). No file dialog: the text goes through the clipboard like the rest of the app's small transfers.
- **Costs across hosts are summed by the app, and a selected client is asked for exactly.** `costs.summary` is per host and has one `projectKey` filter, so the Costs screen's "All hosts" asks every online host that has costs and merges the answers (totals, days, projects, models, origins, personas, the 20 costliest sessions with the host each ran on). With a client selected, each host is asked for its projects first and then once per project of the client, so every breakdown, the cache savings and the message counts stay exact instead of being estimated from the project rows. The price is one request per project of the client per host. Days are each host's own day, so a roll-up across time zones can be off by a day at its edges. The split "By client" is shown while all clients are selected (it is the whole spend), the CSV export and the quota charts stay per host, and a host that is not online, has no costs or does not answer is named in a note, never dropped silently.
- **A client's month limit warns and does not hold anything.** The limit lives in the same `flightdeck.clients` value (a `budgets` map, `0` or negative refused), the thresholds announced in `flightdeck.clientBudgetAlerts`. The app looks at it when a host with costs comes online, when a limit is set or changed, and every 10 minutes: month-to-date spend per client across hosts, thresholds 50%, 80% and 100%, each notified once a month. A threshold stays announced for the month while the budget exists, even if a later look reads lower (a look that missed a host must not announce again when the host is back); a new month, or a budget that is removed, clears it. Crossed limits join "Needs you" through the same path as a host's budget and open the Clients screen. Nothing is created on any host: the daemons' budgets and their queue stay per host and project, and a copy of a client limit into them would drift as projects come and go.
- **A client's defaults pre-fill and order, and never restrict.** The persona (`defaults.persona`, a picker value: `host:<id>` or `app:<id>`) is preselected in "New session" from the **folder** being chosen (its client, by the project the folder is in or by a folder rule), and in "Claude here" from the project's folder; a persona the route asked for, or one the person picked, wins, and it can always be changed. "Claude here" takes the host's own personas by plain id, so an app persona as a default is simply not preselected there. The snippet tag (`defaults.snippetTag`) puts the selected client's tagged snippets first on the Snippets screen and in the palette, and starts a new snippet with that tag; nothing is hidden. A card keeps the project's persona-by-column (a daemon setting): a client default does not reach cards.
- **The budget look is one request per host.** It asks `costs.summary` of each host once for the month and splits the rows by client in the app, so a client of 30 projects across 3 hosts costs 3 requests every 10 minutes, not 90 (a test counts them). The per-project fan-out exists only on the Costs screen, for a selected client, and with no filter set that screen now asks once, not twice.
- **The vault scope is derived, never stored.** A client's `vaultScope` (off by default, opt-in) keeps the secrets that carry its `vaultTag` in its projects. The rules it adds are not saved with the secret: `store.vaultRules` keeps only what the person wrote, and what a host is sent is those rules with the client's in front, computed when they are sent. In front come, for each project the client has right now, a copy of each own rule limited to that project (or an `ask` where the secret has no rule that applies there), then a `deny` for the requesters `claude`, `automation` and `workflow` with no project condition, then the own rules. The denials make it fail closed: a project the list does not know yet falls to them. The requester `you` (a use the person starts in the app) has no denial. Rules are still validated by the daemon and held to its ceiling, so a copy of an `allow` cannot loosen what the daemon would not allow.
- **Turning the scope on is shown and confirmed, off needs nothing.** The dialog says how many secrets carry the tag and how many rules they get, and what the rules do; confirming sends them. Turning it off sends each secret its own rules again, on the hosts that had the generated ones; a secret that was never scoped is not sent anything. When a client that stays scoped gains or loses a project, the rules are generated and sent again after a short wait (one look for a burst of changes), and a notice says so: a widening is never silent. A host that connects is sent the scoped rules from the start.
- **The check that a client's secrets stay in the client is read-only.** For the secrets with the client's vault tag it names a rule that allows or asks for a project of another client, and `allowedHosts` that include a host holding none of the client's projects (said only when some host is known to hold them). It changes nothing; the person edits the rule or the secret.
- **This desktop is the single writer of a scoped secret's rules.** `vault.rules.set` replaces the host's whole set, so the host holds the generated rules and the person's own together. Anything the app reads back (`readHostVaultRules`, from `vault.rules.get`) has the generated rules (ids starting `client-scope:`) stripped, so they are never folded into the own rules: turning the scope off, or editing an own rule, always sends exactly the own rules, with or without the generated ones in front. The scope holds only while this app writes: if another app, or an old version, saves a scoped secret's rules, the generated ones vanish from the host. The app checks when a host connects: a host that holds rules but none marked is told, in an error notice, that they were replaced, and the scope is sent again; marked rules that differ from what would be generated are the client's projects having changed while the host was away, and take the usual notice. A host that holds nothing yet is sent the rules without a warning, and one that cannot answer `vault.rules.get` is sent them all the same. A host that refuses the generated rules (the daemon accepts at most 200 per secret, so a client with many projects can exceed it) is named in an error notice, since the secret is then not held in its client on that host.
