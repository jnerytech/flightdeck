# Keep the computer awake while sessions run (issue #163)

- **The host holds it, not the app.** The issue proposed a Tauri command; the computer that must stay awake is the one that runs the daemon (the local host of a Windows laptop), and the daemon already knows when a session runs. So no Rust: the daemon starts a child process that holds the computer awake for as long as it runs and leaves when the daemon does (`systemd-inhibit ... tail --pid`, `caffeinate -i -w <pid>`, PowerShell with `SetThreadExecutionState(0x80000001)`). A host on another machine keeps that machine awake.
- **One switch, on by default**, in the host's config (`keepAwake`) and on the host page; no "Always" mode. The issue's Off / While sessions run / Always became on / off: "Always" is a different promise (holding while idle) that nobody asked for.
- **What counts as active**: a session that is starting, running or waiting for a permission (`SessionManager.activeSessionCount`, reported after every change of status through `onActivity`). Workflow runs and card runs are sessions of the same manager, so they count. A terminal session started from the app is not a managed session and does not hold it.
- **Failure is a reason, not an error**: no inhibitor on the machine, an unknown system, a holder that cannot start or that ended. The status carries the code and the page words it in both languages. After a failure the daemon does not retry until the sessions stop and begin again, so a broken `systemd-inhibit` is not spawned on every status change.
- **Not done**: the tray tooltip and a status bar segment of the issue (the status bar belongs to #118), and the macOS lid.
- **WSL holds nothing (review of #163).** A daemon inside WSL has `platform` linux, but an inhibitor there holds the WSL machine only and Windows sleeps anyway. On a WSL kernel (`detectWsl`) the reason is `wsl` and nothing is started; the person turns it on for the Windows host, which is the one that must stay awake. The WSL daemon is a separate daemon with its own sessions, so the Windows daemon's count never includes them.
