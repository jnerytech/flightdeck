# A leaking test is the OOM killer's first choice (issue #247)

- **What happened.** On 2026-11-05 at 04:07 the kernel killed a `bun test` that held 10.2 GB of
  memory. Its `oom_score_adj` was 0, the same as the Claude sessions beside it. It was a plain area
  run of `apps/desktop/test/lado-a-lado-ui.test.tsx`, outside the slot and the lane: a red
  `expect([tool, queryByRole(...)]).toEqual([tool, null])`, where Bun's diff formats the happy-dom
  element's whole object graph. Reproduced: one element of a 200-node page passed a 3 GB cap in 50 s.
- **The score.** `scripts/lib/oom-guard.ts` writes 1000 to `/proc/self/oom_score_adj`, on Linux
  only, and never throws.
  - The slot and the light lane call it before they spawn.
  - The test preload calls it too. Every `bun test` loads it, in the slot, in a session or in CI,
    so the area run of that night would have been covered.
  - It writes its own process, not the child's pid after the spawn, so the command and everything
    it starts inherit the score at fork, with no race.
  - The wrapper carrying 1000 as well is harmless: at an equal score the kernel takes the larger
    process.
- **No cap on the failure output.** Bun has no setting for the size or depth of an assertion diff,
  and its diff ignores `inspect.custom` (tried on happy-dom's `Node.prototype`: still 3 GB). So the
  sources are checked instead. `scripts/lib/dom-equal-ratchet.ts` counts the deep equalities that
  hold an element itself, meaning a query whose result is not read from. The one case found
  (`cota-ui.test.tsx`, an array of meters) now checks `.length`, so `dom-equal-baseline.json` is
  empty, and `docs/TDD.md` states the rule.
- **No memory cap per command yet.** `systemd-run --user --scope -p MemoryMax=…` works on the Pi
  but not on CI runners or Windows. The score already protects the sessions, so the cap is left
  for later, as an opt-in.
- **Ported on 2026-11-06.** The branch was written for an rc/0365 that was never cut. It landed
  on main after the slot-orphans port (#388).
