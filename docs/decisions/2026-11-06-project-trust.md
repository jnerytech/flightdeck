# Project trust: a repo's own configuration loads only where the person trusted it (issue #196)

- **Why.** A managed session loaded `user`, `project` and `local` settings, so a repository's committed `.claude/settings.json` hooks and `.mcp.json` servers were in force. Repos the person did not write reach a session (a GitHub clone, a branch checked out in a card worktree). The typings document a trust filter only for an escalating `defaultMode`; whether the spawned `claude` honours a project's hooks before any prompt is the check in the manual list below, not something this phase proved.
- **The rule.** Trusted folder: everything loads as before. Untrusted: `settingSources: ["user"]` and `strictMcpConfig: true` (Flightdeck's own MCP server still goes through `mcpServers`). `strictMcpConfig` also turns off the person's own MCP servers and plugins in an untrusted folder; that cost is said on the screen, in the listing and in the session notice. A worktree always sets `projectConfigRoot` to the main checkout, so a branch never brings its own hooks, and is trusted only if that checkout is.
- **Where it lives.** The daemon, per host: `project_trust(path, trusted_at, source)`, additive, behind the feature `projectTrust`; commands `project.trust.state`, `.inspect`, `.set`, every path checked against the allowed roots. Absent a provider (a host without the feature, or a runtime started without a trust decision) nothing changes.
- **Migration, and what is not trusted.** The migration trusts the board projects' paths and the distinct folders of earlier sessions (the person's existing work, source `migration`). An allowed root is not trusted by being allowed, and a new clone, a folder added later or a project the daemon never saw starts untrusted. Gap: the containment check is a string comparison with no `*Sync` call, so a board project reached through a symlinked path with no earlier session compares as untrusted until the person trusts it.
- **Inspect reads, never runs.** Names and keys only: env values are never read into the listing, a hook command is shown as its first line (cut at 300 characters) with a visible `[+N lines]` when it has more, because the rest of the script still runs once the project is trusted (security review), agents, skills and commands are named and not read, a settings file over 256 KB, not a plain file, not JSON or a symlink that leaves the project is reported as unreadable and not followed, and lists stop at 100 with an `omitted` count per list that the screen shows as "+N more not shown", so a hostile entry after the 100th cannot hide behind a clean-looking listing.
- **Trusting is explicit and logged** ("project trust: trusted <path> (person)"), asks first, names the project and the host, and is revocable; revoking goes through the record that grants (a parent folder may be the one).
- **Not done.** The hostile scratch project with a real `claude`, which is the only way to learn what the CLI does with a repo's hooks in a headless session (a manual check for the maintainer). `managedSettings` with `allowManagedHooksOnly` for an untrusted folder, which would also stop the person's own user-level hooks, was left out. A trust choice for terminal sessions the person starts themselves is out of scope: they run the interactive CLI with its own dialog.
- **Trusting needs a near connection (security review of #196).** `project.trust.set` with `trusted: true` calls `requireVaultTransport` like `roots.add` and `host.bypass`: from outside loopback and Tailscale it is refused with `transport_refused`, because trusting lets the project's hooks and MCP servers run without a prompt. Revoking and reading (`state`, `inspect`) pass from anywhere, since they only lower risk or show it. `ServerOptions.peerOf` is the seam a test uses to say who the peer is.
- **Second security review of #196 (OpenCode), items a to e.**
  - (a) Background sessions (`claude --bg`, and `--resume` to continue one) go through the Claude CLI, not the SDK, so they got no trust at all. `BgService` now takes the same `sessionTrust(folder)` and adds `--setting-sources user --strict-mcp-config` (untrusted) and `--project-config-root <main>` (worktree of a card) before the `--`. The `flightdeckd claude` wrapper forwards them. A continued session asks about the folder the listing reports for it.
  - (b) The listing no longer shows a first line: a command is shown whole, every line, up to 4096 characters, then cut with `[+N more characters]`. The screen puts a command with several lines or past 300 characters in a scrollable block of its own (focusable, so the keyboard scrolls it) and says, above the list, that all of it runs once trusted.
  - (c) The listing names every settings key that runs or redirects something, not only hooks and servers: `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`, `statusLine.command`, `fileSuggestion.command` (whole command); environment variables on a deny-list that sends traffic or code elsewhere (`ANTHROPIC_*_BASE_URL`, proxies, `NODE_OPTIONS`, `BASH_ENV`, `LD_PRELOAD`, `PATH`, ...) with their value, every other variable by name only; plugins and marketplaces; and `otherKeys`, every top-level settings key this listing does not explain, so a key it has never heard of is still named. The header of agent, skill and command files is read (first 256 KB, never followed out of the project) for `hooks`, `mcpServers`, `allowed-tools`, `allowedTools` and `tools`. A deny-list of env names is a floor, not a guarantee: the rest stays name-only because a value may be a secret.
  - (d) A migration seeded the folders of earlier sessions by prefix, so a session once opened in an allowed root trusted every clone under it. Migration 2 adds `scope` to `project_trust`: board projects stay `tree`, the folders of earlier sessions become `exact`. And a record never reaches below an allowed root by prefix: `via()` ignores a `tree` record that has an allowed root inside it. `project.trust.set` with `trusted: true` refuses an allowed root, or a folder above one, with `trust_root_refused`.
  - (e) A worktree the board did not know was trusted by prefix. `ProjectTrust.prepare(cwd)` reads, before a session runs, the `.git` entries from the folder up to the covering record: a directory is a nested clone (its own boundary, not covered by the parent's record), a file with `gitdir: .../.git/worktrees/...` names the main checkout, whose trust it takes. The managers await it before `create`, `createResumed` and `resume`; `send()` stays synchronous on the cache, and the daemon warms the cache for the folders of the sessions that exist at boot before it listens. `.flightdeck/worktrees` and `.claude/worktrees` areas are read as the repository that holds them.
  - **Not done.** Terminal sessions the person starts themselves (their own dialog); the pid/retry minors of keep-awake; the other OpenCode mediums.

## Research note: what a repo's .claude loads in a managed session

Read from the SDK's own typings in `node_modules` (`@anthropic-ai/claude-agent-sdk` 0.3.312, `sdk.d.ts`) and from our code. No `~/.claude` file was read and no real `claude` was run.

- **What the CLI loads by default.** `settingSources` omitted means "all sources are loaded (matches CLI defaults)": `user` (`~/.claude/settings.json`), `project` (`.claude/settings.json`, committed in the repo) and `local` (`.claude/settings.local.json`); `project` is also what loads `CLAUDE.md`. Project settings can carry `hooks` (shell commands that run on events such as SessionStart), `env`, `permissions` (allow rules and `defaultMode`), `enableAllProjectMcpServers` / `enabledMcpjsonServers` and `enabledPlugins`; the repo also brings `.mcp.json` servers (unless `strictMcpConfig`) and `.claude/agents`, `commands` and `skills`.
- **What protects an interactive user, and what the typings say about the SDK.** The CLI applies "a separate trust filter before honoring escalating modes (`bypassPermissions`, `auto`, `acceptEdits`) from repo-committed files" (`filterEscalatingDefaultMode`). Nothing in the typings says the SDK asks the folder-trust question of the interactive CLI; they only say the default "matches CLI defaults". Whether a spawned `claude` runs a repo's hooks and servers at the start of a headless session is therefore **not verified here**: it needs the hostile scratch project of the issue, with a real `claude`, by hand.
- **What the SDK offers to close it.** `settingSources: ["user"]` (or `[]`, "SDK isolation mode"); `strictMcpConfig: true` ("only MCP servers passed via `mcpServers`", ignoring project `.mcp.json`, plugins and on-disk agent frontmatter); `managedSettings` with `allowManagedHooksOnly` (`disableAllHooks: true` binds as that, so the machine administrator's hooks still run) and `deniedMcpServers`; and `projectConfigRoot` ("the trusted checkout `cwd` is a worktree of": project settings, hooks, permissions, `.mcp.json` and the `.claude` trees then come from there, not from the branch checked out in `cwd`).
- **What Flightdeck passes today.** Managed sessions start with `settingSources: ["user", "project", "local"]` (`claude-sdk-runtime.ts:273`) and no `strictMcpConfig`, `managedSettings` or `projectConfigRoot`, on purpose for the person's own repos (their hooks, their servers, `CLAUDE.md`). The one-shots that must not read a repo use `[]` (`judgePermission`, the account readers). Repos reach a managed session from outside the person's own work through "start from GitHub" (`github/start.ts` clones `https://github.com/<repo>.git` into an allowed root) and through card worktrees of a branch someone else wrote.
- **The gap.** A repo the person did not write, once cloned and opened, is treated like their own: if the headless `claude` honours the project's hooks, `.mcp.json` and allow rules, a hostile repo runs commands on the host when a session starts, with no prompt of ours in between. The issue's remedy, in this order: (1) verify with the hostile scratch project; (2) a per-project trust (off by default, stored by the daemon) and, for an untrusted project, `settingSources: ["user"]` plus `strictMcpConfig: true` (Flightdeck's own MCP server still passes through `mcpServers`), and `projectConfigRoot` for worktrees; (3) show what a project would load (its hook events and commands, MCP server names, `env` keys, allow rules, agents) before the person trusts it. The cost of an untrusted project is real and has to be said in the screen: no project `CLAUDE.md` and none of its agents or skills until it is trusted.
