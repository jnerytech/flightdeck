# Git revisions are a branded type, and the ratchet reads every way git is started (issue #369)

#345 guarded every git call that takes a project's base or a branch with `refArg`, and added a
ratchet that goes by variable names. The review left three gaps; this closes them.

- **`Rev`** (`board/ref-arg.ts`) is `string` branded: only `refArg` (no empty name, no leading `-`)
  and `assertBranchName` (the rules of `git check-ref-format --branch`) return one, and `HEAD` is the
  one constant. The helpers that take a base or a branch (`aheadBehind`, `assertLocalBranch`,
  `rebaseOnto`, `mergeIntoBase`, `freshBase`, `cardDiff`, `workflowSources`) take a `Rev`, not a
  `string`. A caller that has a plain string no longer compiles, whatever the variable is called, so
  the check happens where the value comes in (the project's settings, the card's branch) and the
  compiler finds the one that forgot. `apps/daemon/test/rev-type.test.ts` is a type test: it holds a
  `// @ts-expect-error` for each helper, and `bun run typecheck` fails when a helper takes a string
  again. The helpers keep their own `refArg` as a second layer (a `Rev` can still be forged with
  `as Rev`, and the guard tests do it to prove the runtime refusal).
- **The ratchet reads the other ways to start git** (`scripts/lib/git-args.ts`): `Bun.spawn`,
  `spawnSync`, `runCommand` and an injected `exec` whose array starts with `"git"` (or
  `whichOnPath("git")`), read like `git(...)`: a name that carries a branch, or a spread of a
  variable, in what follows needs `refArg`, `--end-of-options` or `--`, or a `// git-arg: <why>`
  line. The six forwarders that pass a list of arguments on (the shared helpers in
  `board/command.ts`, the checkpoints' two, the project key's, the clone runner's, the fake
  runtime's) say so with that line: their callers are what is checked, and a seventh shape cannot
  appear without someone writing why.
- **A base stored before the check** is marked: `Project.baseBranchInvalid` is sent when the stored
  base is neither `HEAD` (a detached checkout) nor a branch name, and the project page says "the base
  branch X is not a valid branch name, so the board's git steps refuse it, set a real one in
  Settings", in both languages. Before, the person met `branch_invalid` at the first card they
  started. Setting a real base (`project.update`, which checks it) clears the mark.
- **Not done:** the daemon does not rewrite a stored base itself (it does not know which branch was
  meant). `as Rev` is still possible by hand; a lint rule against it would be a separate change.
  The scanner still goes by names for `git(...)` calls whose argument is none of the known ones.
