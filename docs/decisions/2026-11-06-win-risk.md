# A Windows path in a rule is read both ways (issue #431)

`ruleLevel` (issue #384) returned `any` for a path rule with a wildcard and a backslash, because a
backslash is an escape in the CLI's pattern syntax and this check did not follow it. Every project
on Windows has backslashes in its path, so `Write(C:\Users\me\proj\app-*.txt)` was refused with
`perm_rule_too_broad`, and the always-allow test of #394 failed on Windows only.

A rule with a backslash is now read two ways: with each backslash as a separator (what a person on
Windows means) and with each removed (an escape). The wildcards of both readings are enumerated as
before and the highest level wins, so a reading that can reach a credential or a control file
still makes the rule `any`. A rule with no backslash is read as before.

Consequence: a wildcard rule on a drive path is accepted when no reading can reach a credential,
and refused when one can (`C:\Users\me\proj\*.txt` can be `.env.txt`, as `/proj/*.txt` can).
`apps/daemon/test/rule-risk-windows.test.ts` runs these shapes on Linux.
