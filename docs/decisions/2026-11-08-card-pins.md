# A card pins library documents (issue #76)

A card can name library documents (ADRs, RFCs, PRDs, specs) that its session must read. This is the
daemon side; the picker in the card is the next slice.

## Decision

- **What a pin is.** A relative path to a Markdown file inside one of the library's fixed folders
  (`docs/decisions|adr|rfc|prd|specs`, now `KNOWLEDGE_FOLDERS` in the protocol and shared with the
  library listing). `pinnedDocProblem` adds the folder rule to `specPathProblem` (no `..`, no
  absolute path, no Windows device or stream names, no control characters). Paths use `/` and are
  case-sensitive. At most 10 per card (`PINNED_DOCS_MAX`); duplicates are dropped, order is kept.
- **Where it is kept.** `cards.pinned_docs`, a JSON list (NULL: none). `card.update` takes
  `pinnedDocs` and replaces the whole list; a patch without it leaves the pins; a path outside the
  library or an eleventh pin is refused with `pinned_doc_invalid`.
- **What the session is told.** The first prompt of a card run is the description, then a block
  naming each pinned document that is in the worktree with its first heading, then the project's
  template. Only the path and the heading go in: never the contents, which the session reads itself
  (the same rule as the spec file, whose `readSpec` is reused: a regular file with one name, not a
  link, inside the worktree, opened without following a link). A pin the worktree does not hold is
  left out; there is no error, because the document may live on another branch.
- **Not decided here.** A pinned document marked obsolete is still named: the person chose it. A
  warning for that, and for a valid document that links to an obsolete one, is a later slice of #76.
- **Announced** as the `cardPins` feature of a host with a board, so the app shows the picker only
  where the host takes it.
