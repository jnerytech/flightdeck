# CLI first: a new feature is a flightdeckd command, and the app calls the same daemon command (issue #3423)

Slice A of #3423 (issue #3424). User decision, 2026-11-19.

## Rule

A new feature starts as a `flightdeckd` command. The app screen for it calls the same daemon request
that the command calls, so a person at a terminal, a script and the app all do the same thing and
get the same answer.

## Contract of a command

- **`--json`:** one JSON value on stdout and nothing else. The keys are stable; a field a daemon does
  not report is `null` (or an empty list), never a missing key. Without `--json` the output is
  plain lines for a person.
- **Exit codes:** `0` done, `1` refused (bad arguments, a refusal from the daemon), `2` no daemon
  (unreachable, cut, or too slow). A write that may or may not have happened says so on stderr.
- **Text from the daemon is data:** control and bidirectional characters are replaced by a space
  before they reach the terminal.
- **Local daemon only.** The command reads the token from the daemon config file, never from an
  argument or the environment (`--token` is refused), and talks only to a loopback address. Reaching
  another host needs a pairing token and is a later slice, with its own security review.

The shared code is `runOnLocalDaemon` in `apps/daemon/src/daemon-client/`; `flightdeckd card` was the
first command on it, and `host` and `sessions` the next.

## Names

- `host`: what this daemon says about itself (version, system, Claude, features, bypass switch).
- `sessions`: the sessions of this daemon, one small object each.
- Slice B (#3425): `send`, `approve`, `deny`, `requests`. Slice C (#3426): persona shortcuts.
- The manual writes `fd host`, `fd sessions`: `fd` is the short name of `flightdeckd`, settled in
  #3433 (until it ships, type `flightdeckd`). The code stays in `flightdeckd`'s `cli/`.

## Left out on purpose

- The count of open requests per session: `session.list` does not carry it. It arrives with the
  request commands of slice B, which read the pending requests themselves.
- The paths and the settings of the host (`claudePath`, `logPath` and the like): not for a script.

## Answering a permission request from a shell (slice B, issue #3425)

`flightdeckd approve` and `deny` use the same loopback token as every other command, so a managed
session that can read the config could answer its own requests. Two measures, and one limit:

- The risk rules rate `fd` or `flightdeckd` with the verb `approve` or `deny` as high risk, so the
  session's own request for it goes to the person. `send` and `requests` stay ordinary shell
  commands: sessions messaging each other is the point of the epic.
- `--hold` is the caller's own word that a person read the request. The daemon does not check it,
  and the refusal for a high-risk request tells a session to ask the person.
- Limit: a process that reads the config can still call the WebSocket directly. A real barrier is a
  separate approval credential that the daemon gives only to the app, which is a design choice for
  the coordinator or the user and is not part of this slice.
- `flightdeckd requests` lists managed sessions only; `approve` and `deny` also answer an external
  (`ext-...`) request by id.

## Ending or forcing a card from a shell (issue #3454)

`flightdeckd card discard`, `complete` and `delete` need `--confirm`, and `card move --force` skips a
column's contract. The app asks the person for each of these. The CLI refuses the first three without
`--confirm`, but the flag is only the caller's own word, as `--hold` is above:

- The risk rules rate these four commands as high risk, under either name and through a runtime or a
  shell, so a managed session's own call goes to the person (the same heuristic over the command text
  as `approve` and `deny`). `card stop`, `update` and a move without `--force` stay ordinary commands.
- The same limit holds: a process that reads the config can call the WebSocket directly, and a real
  barrier is the separate approval credential named above.

## Creating a team from a shell (issue #3455)

`flightdeckd team new` starts a coordinator and up to eight workers, each with its own permission mode
(one may be `bypassPermissions`) and each spending plan quota. The app asks the person to fill a form
and, for a bypass member, to confirm again. The CLI refuses a bypass member without `--confirm`, but the
flag is only the caller's own word, as above:

- The risk rules rate `team new` as high risk, under either name and through a runtime or a shell, so a
  managed session's own call goes to the person. `team list` and `team show` stay ordinary commands.
- The same limit holds: a process that reads the config can call the WebSocket directly, and a real
  barrier is the separate approval credential named above.
- A member is one spec, `persona[:model[:effort[:mode]]]`, the idea of `card start-arena --variant`, but with
  the persona first (`--variant` is `model[:effort[:persona]]`).
  A persona for some workers only is refused, since the daemon takes one for every worker or for none.

## Changing a team from a shell (issue #3455)

`team update`, `add-member`, `remove-member` and `delete` are the app's team settings and member list as
daemon requests (`teams.update`, `teams.delete`):

- `team delete` has no confirmation field in the request, so `--confirm` is only the CLI's own gate: it is
  checked before anything is sent and is not part of the payload. The daemon refuses an open team and a
  live member on its own.
- `add-member` and `remove-member` use `teams.update` (`addMember`, `removeMember`), not the
  `teams.add_member` and `teams.remove_member` requests, which carry the identity of the team's
  coordinator and are marked app-only in `docs/cli-parity.json`. A person at a terminal has no such identity.
- The risk rules rate `update`, `delete`, `add-member` and `remove-member` as high risk with `new`: they
  start or stop sessions and drop a record, and `update` rewrites the goal and checks that the coordinator
  reads as a system notice and swaps a live member's persona (the security review found that `teams.update`
  has no coordinator-only check, so a worker could otherwise steer the team).
- `--confirm` for a bypass member covers an explicit mode in the spec, as in `team new`; a persona whose own
  mode is bypass is not covered, as in the app.
  `--goal`, a flag of `team update`, is refused on `team new`, whose goal is its operand.

### Pausing, closing and messaging a team from a shell (issue #3455)

- `team pause`, `resume` and `close` are `teams.pause`, `teams.resume` and `teams.close`; `team close` sends
  `confirm: true` because the daemon asks for it, and the CLI refuses without `--confirm` before sending.
- `team message <team> <text>` is `teams.message`, a notice to every member with a session. Both forms stay:
  `flightdeckd message team <team>` is the team's status for the asking session (`teams.status`), `team message`
  sends. A blank text is refused before it is sent.
- `teams.watch` stays app-only in this issue: it is not among the verbs of #3455, and `team show` reads the state
  on demand. `board watch` (#3454) now streams from a command, so a `team watch` can follow it later. `teams.report` stays app-only: only the coordinator reports, as
  itself, and a terminal has no session identity.
- The risk rules rate `pause`, `resume`, `close` and `message` as high risk with the other team verbs: they stop,
  start or end a team's work, or put text into every member's session as a system notice.

## Reading the quota and the usage from a shell (issue #3460)

Slice 1 of the cost commands: `quota get`, `quota history`, `quota pause-at` and `usage`, one word per area
(`quota`, `usage`; the issue's question Q1), each over the request the screen already uses (`quota.get`,
`quota.history`, `quota.setPauseAt`, `usage.summary`).

- `costs`, `roi`, `budget` and the watch verbs come in later slices; `quota.watch` stays a gap in
  `docs/cli-parity.json` until then (Q2).
- `quota pause-at` takes a share as plain decimal digits from 0 to 1 or `off`, and refuses anything else
  before sending. It is a write with no confirmation field. Raising or turning off the guard is not a
  restriction: queued cards and team members start at once and spend the plan, and the value is kept in the
  config file. So the risk rules rate every `quota pause-at` from a session's shell as high, as for `team`
  and `persona`; the rating is the gate, and the command takes no `--confirm`. `quota get`, `quota history`
  and `usage` only read (security review, #3460).
- `--hours` (1 to 720) and `--days` (1 to 90) are the protocol's own limits, checked before sending.
