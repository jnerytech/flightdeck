# CLI first: a new feature is a flightdeckd command, and the app calls the same daemon command (issue #3423)

Slice A of #3423 (issue #3424). User decision, 2026-11-19.

## Rule

A new feature starts as a `flightdeckd` command. The app screen for it calls the same daemon request
that the command calls, so a person at a terminal, a script and the app all do the same thing and
get the same answer.

## Contract of a command

- **`--json`:** one JSON value on stdout and nothing else. The keys are stable; a field a daemon does
  not report is `null` (or an empty list), never a missing key. Without `--json` the output is
  plain lines for a person.
- **Exit codes:** `0` done, `1` refused (bad arguments, a refusal from the daemon), `2` no daemon
  (unreachable, cut, or too slow). A write that may or may not have happened says so on stderr.
- **Text from the daemon is data:** control and bidirectional characters are replaced by a space
  before they reach the terminal.
- **Local daemon only.** The command reads the token from the daemon config file, never from an
  argument or the environment (`--token` is refused), and talks only to a loopback address. Reaching
  another host needs a pairing token and is a later slice, with its own security review.

The shared code is `runOnLocalDaemon` in `apps/daemon/src/daemon-client/`; `flightdeckd card` was the
first command on it, and `host` and `sessions` the next.

## Names

- `host`: what this daemon says about itself (version, system, Claude, features, bypass switch).
- `sessions`: the sessions of this daemon, one small object each.
- Slice B (#3425): `send`, `approve`, `deny`, `requests`. Slice C (#3426): persona shortcuts.
- The manual writes `fd host`, `fd sessions`: `fd` is the short name of `flightdeckd`, settled in
  #3433 (until it ships, type `flightdeckd`). The code stays in `flightdeckd`'s `cli/`.

## Left out on purpose

- The count of open requests per session: `session.list` does not carry it. It arrives with the
  request commands of slice B, which read the pending requests themselves.
- The paths and the settings of the host (`claudePath`, `logPath` and the like): not for a script.

## Answering a permission request from a shell (slice B, issue #3425)

`flightdeckd approve` and `deny` use the same loopback token as every other command, so a managed
session that can read the config could answer its own requests. Two measures, and one limit:

- The risk rules rate `fd` or `flightdeckd` with the verb `approve` or `deny` as high risk, so the
  session's own request for it goes to the person. `send` and `requests` stay ordinary shell
  commands: sessions messaging each other is the point of the epic.
- `--hold` is the caller's own word that a person read the request. The daemon does not check it,
  and the refusal for a high-risk request tells a session to ask the person.
- Limit: a process that reads the config can still call the WebSocket directly. A real barrier is a
  separate approval credential that the daemon gives only to the app, which is a design choice for
  the coordinator or the user and is not part of this slice.
- `flightdeckd requests` lists managed sessions only; `approve` and `deny` also answer an external
  (`ext-...`) request by id.

## Ending or forcing a card from a shell (issue #3454)

`flightdeckd card discard`, `complete` and `delete` need `--confirm`, and `card move --force` skips a
column's contract. The app asks the person for each of these. The CLI refuses the first three without
`--confirm`, but the flag is only the caller's own word, as `--hold` is above:

- The risk rules rate these four commands as high risk, under either name and through a runtime or a
  shell, so a managed session's own call goes to the person (the same heuristic over the command text
  as `approve` and `deny`). `card stop`, `update` and a move without `--force` stay ordinary commands.
- The same limit holds: a process that reads the config can call the WebSocket directly, and a real
  barrier is the separate approval credential named above.

## Creating a team from a shell (issue #3455)

`flightdeckd team new` starts a coordinator and up to eight workers, each with its own permission mode
(one may be `bypassPermissions`) and each spending plan quota. The app asks the person to fill a form
and, for a bypass member, to confirm again. The CLI refuses a bypass member without `--confirm`, but the
flag is only the caller's own word, as above:

- The risk rules rate `team new` as high risk, under either name and through a runtime or a shell, so a
  managed session's own call goes to the person. `team list` and `team show` stay ordinary commands.
- The same limit holds: a process that reads the config can call the WebSocket directly, and a real
  barrier is the separate approval credential named above.
- A member is one spec, `persona[:model[:effort[:mode]]]`, the idea of `card start-arena --variant`, but with
  the persona first (`--variant` is `model[:effort[:persona]]`).
  A persona for some workers only is refused, since the daemon takes one for every worker or for none.

## Changing a team from a shell (issue #3455)

`team update`, `add-member`, `remove-member` and `delete` are the app's team settings and member list as
daemon requests (`teams.update`, `teams.delete`):

- `team delete` has no confirmation field in the request, so `--confirm` is only the CLI's own gate: it is
  checked before anything is sent and is not part of the payload. The daemon refuses an open team and a
  live member on its own.
- `add-member` and `remove-member` use `teams.update` (`addMember`, `removeMember`), not the
  `teams.add_member` and `teams.remove_member` requests, which carry the identity of the team's
  coordinator and are marked app-only in `docs/cli-parity.json`. A person at a terminal has no such identity.
- The risk rules rate `update`, `delete`, `add-member` and `remove-member` as high risk with `new`: they
  start or stop sessions and drop a record, and `update` rewrites the goal and checks that the coordinator
  reads as a system notice and swaps a live member's persona (the security review found that `teams.update`
  has no coordinator-only check, so a worker could otherwise steer the team).
- `--confirm` for a bypass member covers an explicit mode in the spec, as in `team new`; a persona whose own
  mode is bypass is not covered, as in the app.
  `--goal`, a flag of `team update`, is refused on `team new`, whose goal is its operand.

### Pausing, closing and messaging a team from a shell (issue #3455)

- `team pause`, `resume` and `close` are `teams.pause`, `teams.resume` and `teams.close`; `team close` sends
  `confirm: true` because the daemon asks for it, and the CLI refuses without `--confirm` before sending.
- `team message <team> <text>` is `teams.message`, a notice to every member with a session. Both forms stay:
  `flightdeckd message team <team>` is the team's status for the asking session (`teams.status`), `team message`
  sends. A blank text is refused before it is sent.
- `teams.watch` stays app-only in this issue: it is not among the verbs of #3455, and `team show` reads the state
  on demand. `board watch` (#3454) now streams from a command, so a `team watch` can follow it later. `teams.report` stays app-only: only the coordinator reports, as
  itself, and a terminal has no session identity.
- The risk rules rate `pause`, `resume`, `close` and `message` as high risk with the other team verbs: they stop,
  start or end a team's work, or put text into every member's session as a system notice.

## Reading the quota and the usage from a shell (issue #3460)

Slice 1 of the cost commands: `quota get`, `quota history`, `quota pause-at` and `usage`, one word per area
(`quota`, `usage`; the issue's question Q1), each over the request the screen already uses (`quota.get`,
`quota.history`, `quota.setPauseAt`, `usage.summary`).

- `costs`, `roi`, `budget` and the watch verbs come in later slices; `quota.watch` stays a gap in
  `docs/cli-parity.json` until then (Q2).
- `quota pause-at` takes a share as plain decimal digits from 0 to 1 or `off`, and refuses anything else
  before sending. It is a write with no confirmation field. Raising or turning off the guard is not a
  restriction: queued cards and team members start at once and spend the plan, and the value is kept in the
  config file. So the risk rules rate every `quota pause-at` from a session's shell as high, as for `team`
  and `persona`; the rating is the gate, and the command takes no `--confirm`. `quota get`, `quota history`
  and `usage` only read (security review, #3460).
- `--hours` (1 to 720) and `--days` (1 to 90) are the protocol's own limits, checked before sending.

Slice 2: `costs summary|session|card|run|status|export` and `roi`, all reads over `costs.*` and `roi.summary`, so
they need no risk rating. `costs sessions` (a batch of ids) and `costs reprice` stay gaps in the parity file
until slice 4. The days (`--from`, `--to`) are checked as `YYYY-MM-DD` and as real calendar days before sending,
and `--origin` against the protocol's own list. `--model` is persona's flag too; the persona check lets it pass
on `costs` and the costs check refuses it on the verbs that do not filter.

### Slice 3: `budget list|set|set-quota|remove` (issue #3460)

One word per area again (`budget`), each verb over the request the screen already uses (`budget.list`,
`budget.set`, `budget.setQuota`, `budget.remove`); `budget.watch` stays a gap with the other watch verbs.

- `set` and `set-quota` are two verbs because the protocol has two inputs: a limit in dollars per day or
  month, and a share of a quota window. Each flag belongs to its verb, and a flag of another verb is refused
  before anything is sent. `--scope` and `--project` are the shared flags; `--scope all` is the persona's and
  is refused here.
- A dollar amount is plain decimal digits and at least one cent (no `0x5`, no `1e3`); a share is from 0.001 to 1, the
  protocol's own limits. `--id` changes a budget the daemon already has; `remove` takes the id as its operand.
- A write that gets no answer exits `2` and says the budget may or may not have changed: `budget list` shows
  which.
- A budget is a spend guard, like the quota guard: `set` and `set-quota` can raise a limit that holds new
  cards back, and `remove` drops one, so a session could spend past what the person set. The risk rules rate
  all three from a session's shell as high; the rating is the gate, and the commands take no `--confirm`.
  `budget list` only reads.

### Slice 4: `quota watch`, `budget watch` and `costs reprice --confirm` (issue #3460)

The last verbs of the issue. `costs sessions` stays a gap: `costs session <id>` already reads one session and the
screen's list has no CLI use yet.

- `quota watch` and `budget watch` are streams over `quota.watch` and `budget.watch`, on the stream helper of
  `board watch` (`docs/decisions/2026-11-20-cli-streams.md`): the time limit covers the connect and the ack,
  Ctrl-C ends with `0`, a refused watch is `1`, a closed socket is `2`. They are reads, so a watch with no
  answer does not say a write may have gone in. A line is the text of `quota get` or `budget list` for that
  frame, and with `--json` the frame without its `type`.
- `costs reprice` rewrites the cost of every recorded message from the price table of the config, in one
  transaction, which moves what the budgets and the quota guard read. It asks for `--confirm`, like `rules remove`
  (#3457): without it the parser exits `1` and sends nothing. The risk rules rate it high from a session's shell,
  as the other spend guards; `--confirm` is only a flag the caller types, so the rating is the gate. A reprice that
  gets no answer exits `2` and says the costs may or may not have been priced again: `costs status` shows which.

### Slice: `session interrupted|summary|files` (issue #3514)

The sessions get a noun of their own, `session <verb>`; `sessions` stays the list and `send` stays top level.
This is the read side of the 17 `session.*` rows, over the requests the app uses (`session.interrupted`,
`session.summary`, `session.files`). The write verbs follow in later slices under the same noun.

- A session is its id or its name, resolved through `session.list` like `send`. `summary` and `files` ask the
  daemon about the session's Claude session id (the protocol's key), so a session that has none yet is refused
  with exit 1 and nothing is asked. A name two sessions share is refused with the ids.
- `--json` prints what the protocol returned, with its own keys (`{"sessions": [...]}`, the recap,
  `{"files": [...]}`); a missing field is `null`. The text forms print a dash for a missing field.
- All three only read, so none needs a risk rating, and a read with no answer exits 2 without saying a write may
  have gone in.
- `session.subscribe` and `session.unsubscribe` stay `appOnly` (fd-coordinator, on the issue): they are the app's
  stream plumbing, and live output would be a watch verb in a later slice.

### Slice: `session interrupt|close|resume|sleep|set-model|set-effort|meta set` (issue #3514)

The first write verbs of `session <verb>`, over the app's own requests (`session.interrupt`, `session.close`,
`session.resume`, `session.sleep`, `session.setModel`, `session.setEffort`, `session.meta.set`). They are the
ordinary ones, except `close`: the others undo or repeat with one more command. `create`, `set-mode`, `fork`,
`apply-persona` and `clear-persona` come later, with their risk ratings.

- `session close` is rated high from a session's shell (security review): the app asks a person to confirm it, it
  drops the queued messages and the open permission requests, and a team coordinator is closed with none of the
  guards `team remove-member` has. The rating is the gate; the command takes no `--confirm`.
- `interrupt` stays ordinary, like `send`: it steps the card's check loop aside as a person turn and cancels the
  session's open permission requests, which is what a coordinator interrupting a worker is for.

- A session is its id or its name, resolved through `session.list`. A name two sessions share is refused with the
  ids and nothing is sent. A write with no answer exits `2` and says the change may or may not have gone in.
- `set-model` and `set-effort` take the value as the next word; `default` gives the session's own back (the daemon
  takes `null` for it). An effort outside `low|medium|high|xhigh|max` is refused by the parser. The model is not
  checked here: the daemon knows which models exist.
- `meta set <session> name=... pinned=... archived=...` takes `key=value` words, at least one. `name=` with nothing
  after it clears the name. `pinned` and `archived` are `true` or `false` only. The protocol keys the request by the
  Claude session id, so a session that has none yet is refused with exit 1 and nothing is sent; the daemon refuses
  a session it does not control with its own text.
- `sleep` exits `0` only when the daemon says `slept` or `already`. When the daemon keeps it awake (`not_idle`,
  `queued`, `kept_awake`, `subscribed`) the command exits `1` and says why on stderr, because the caller asked for
  a state it did not get; an answer this CLI does not know is the same refusal, so a newer daemon's reason never
  reads as a sleep. `--json` prints nothing on stdout for that refusal, as for every refusal.
- `resume` of a session that has not ended is the daemon's refusal, shown as it is, exit `1`.
- `--json` prints `{session, action, ...}` with the new model, effort or the `meta` fields the daemon returned. The
  text line of `meta set` names the fields that were asked, with the values the daemon kept.

### Slice: `session create|fork|set-mode|apply-persona|clear-persona` (issue #3514)

The rest of the write verbs of `session <verb>`, over the app's own requests (`session.create`, `session.fork`,
`session.setMode`, `session.applyPersona`, `session.clearPersona`).

- `create`, `fork`, `set-mode` and `apply-persona` are rated high from a session's shell (security review). `create` and
  `fork` start a session with a folder, a prompt, a model and a permission mode of its own (up to
  `bypassPermissions`) and spend the plan. `set-mode` and `apply-persona` change what a live session may do without
  asking: a persona carries its own permission mode and instructions. The app has the person fill a form or press a
  button; from a shell any session could widen its own reach. The rating is the gate, and the commands take no
  `--confirm`. `clear-persona` stays ordinary: it takes a role away and sends a message that says so, and one more
  `apply-persona` puts it back.
- `session create --cwd <folder>` takes the folder and the optional `--prompt`, `--name`, `--model`, `--effort`,
  `--permission-mode` and `--persona` (with `--language` only beside `--persona`). Everything goes to the daemon
  as typed: the folder is checked against the allowed roots by the daemon, which is the only place that knows them,
  so a folder outside them is the daemon's refusal, exit 1. A relative folder is sent as typed, not resolved against
  the caller's folder. `--runtime` is not offered: it picks another agent, and the slice stays on the app's form.
  The text line is `started session <id>`; `--json` prints `{session, action}`.
- `session fork <claude-session-id> --cwd <folder> [--up-to <message-id>] [--open flightdeck|terminal]` sends
  `open: flightdeck` when `--open` is left out. The issue text says `--open terminal` opens a terminal on the host. It
  does not: the daemon only answers with the command that resumes the fork (`flightdeckd claude --resume <id>`), and
  the CLI prints that command; opening a window is the app's job. `--json` prints `{action, claudeSessionId, session,
  command}` with `null` for the one the daemon did not give. `fork --rewind-turn` rewinds working files, a different
  and heavier act; it is left out of this slice.
- `set-mode <session> <default|acceptEdits|plan|bypassPermissions>` takes the modes the protocol allows for a live
  session (`SettableMode`); `auto` and `dontAsk` are refused by the parser. The daemon refuses `bypassPermissions` on
  a host that does not allow it, shown as it is, exit 1.
- `apply-persona <session> <persona-id> [--language en|pt-BR]` and `clear-persona <session> [--language]` print what
  became of the message the change sends: it went into the session, it waits for the session's turn, or it went to
  the terminal session; an older host that says nothing gets no suffix and `delivery: null` in `--json`.
  `clear-persona` on a session with no persona is the daemon's refusal.
- The flags `--cwd`, `--name`, `--model`, `--effort`, `--permission-mode`, `--persona` and `--language` also belong to
  other commands. Once the line is read, a `session` line moves them into the verb's own options, so no other
  command's check sees them, and each is refused on a verb that does not take it with the list of the verbs that do.
  `--prompt`, `--up-to` and `--open` are new, and are refused on every command but the verbs that take them. A
  `--prompt` that starts with two dashes cannot be typed: the parser rejects a value that starts with `--`, also in
  the `--prompt=...` form.
- `session.subscribe` and `session.unsubscribe` are `appOnly` in the parity table: they ask the daemon to push one
  session's stream to the app's open window, and a command that ends has no window to push to.
- The risk rules read a shell line twice: cut at every separator, and cut only outside quotes. A quoted value that
  holds a separator before the verb (`fd --prompt "a;b" session create`) used to cut the verb off its program and rate
  the line as an ordinary command; this also closed the same gap for `session close`. A verb the shell builds at run
  time (`V=create; fd session $V`) and a runner the list does not know (`pnpm exec fd ...`) are still rated as an
  ordinary command: the rule reads the words as typed.
- `session fork --open terminal` passes `--cwd` to the fork without the allowed-roots check that `create` and the
  flightdeck open mode apply (`Forker.fork` in the daemon); this slice does not change the daemon.
- A write with no answer exits `2`. `create` and `fork` say a session may or may not have been started and point to
  `sessions`; the other verbs say the change may or may not have gone into the session.

## Reading the plugins from a shell (issue #3516)

Slice 1 of the `plugins` noun: `plugins list`, `plugins detail`, `plugins preview` and `plugins preview-update`, over
`plugins.list`, `plugins.detail`, `plugins.preview` and `plugins.previewUpdate`. The seven writes (`install`, `update`,
`uninstall`, `pin` and the three marketplace verbs) are the second slice, below.

- `preview` installs nothing; it prints the hash an install repeats. A plugin whose source is not local prints
  `not local` and no hash, and exits 0.
- `preview --dir <folder>` read any folder the daemon could read, because the handler passed `dir` whole to the
  inspection. It now resolves the folder with `resolveAllowedCwd`, like every other path a caller gives the
  daemon, so a folder outside the allowed roots is refused with `forbidden_cwd` (decision of fd-coordinator,
  2026-11-20). A host with no allowed roots (the default) refuses every folder, as it does for a session's folder;
  the app's folder picker lists only folders inside the roots, so on such a host an install from a folder needs a root first.
- `plugins.install` read a folder the same way, so it resolves `dir` with `resolveAllowedCwd` too (security
  review of this slice): closing only the preview would have left the same folder readable through install.
- `--dir` is made absolute against the shell's folder before it is sent (the daemon's own folder is another one);
  with `--host` it must already be absolute, because it is read on that host.
- The reads need no risk rating: nothing the person has is changed and nothing printed is a secret. Two
  details: `preview-update` first refreshes the marketplace's listing (the daemon runs
  `claude plugin marketplace update`, as the app's update dialog does), so it reaches the network and rewrites the
  marketplace cache; and a marketplace added by a URL with `user:token@` in it is printed without the userinfo.
- `--host <name>` works as for `send`: the verbs go through `runOnLocalDaemon` with the remote target.

### The plugin writes (issue #3516, slice 2)

`plugins install`, `update`, `uninstall`, `pin`, `unpin`, `marketplace-add`, `marketplace-remove` and
`marketplace-update`, over the seven daemon commands of the same names.

- `install` and `update` need `--confirm-hash`, the hash `preview` or `preview-update` printed: the daemon refuses
  the change when the content is not the one that was read (`unchanged` or `failed` with its message, exit `1`).
  `uninstall`, `marketplace-add` and `marketplace-remove` need `--confirm`. The parser exits `1` without them and
  sends nothing. `pin`, `unpin` and `marketplace-update` need neither: they take nothing away and run nothing.
- A plugin that brings a command to run answers `needs-command-confirmation` with the command and its `sha256`.
  The CLI prints both, says that nothing was installed, and exits `1`; the line is repeated with `--accept-command
  <sha256>`. The person reads the command before the second line, as the app's dialog shows it.
- `--plugin-scope user|project|local` is the scope of an install, an uninstall or a marketplace add (`--scope` is
  the card scope of other verbs, so it is not reused). `--dir` stays inside the allowed folders, as in the preview.
- The risk rules rate `install`, `update`, `uninstall`, `marketplace-add` and `marketplace-remove` high from a
  session's shell: a plugin brings hooks and servers that run with no prompt, and an uninstall takes away what the
  person set up. `--confirm` and `--confirm-hash` are only words the caller types, so the rating is the gate.
  `pin`, `unpin` and `marketplace-update` stay ordinary. A device proof for plugins is not part of this slice.
- A write sets `note.wrote` before it is sent, so a timeout exits `2` with "may or may not have happened" and
  points at `plugins list`. `--json` prints the daemon's `PluginChange` and exits `1` for a change that did not happen.

### The ssh reads (issue #3537, slice 1)

`ssh list` and `ssh import preview`, over `ssh.list` and `ssh.import.preview`. Neither connects, writes or sends a
payload: the daemon answers from its own list, or from `~/.ssh/config`.

- `ssh list` prints one line per target with its name, id, address, auth and the fingerprint it pins (`not pinned`
  before the first confirmation), then `via`, `jump`, `secret` and `tags` when set. `secret` is the id of a vault
  item, never a secret. The id is printed because the verbs that follow name a target by id or by name, and a name
  two targets share is refused with the ids.
- `ssh import preview` prints each name of `~/.ssh/config` the import would turn into a target, and marks one that
  is already registered. It never applies the import.
- `--json` prints the daemon's `{"targets": [...]}` and `{"entries": [...]}` as they are, `null` for a missing
  field; `--host <name>` reads a paired host. The transport guard of the ssh commands is not part of this slice.
- Known gap: `ssh import preview` shows a session the aliases, hosts, users, key paths and jumps of `~/.ssh/config`
  as an ordinary shell command, where a direct `cat ~/.ssh/config` is rated high as a credential path. It shows no
  secret, only names and paths, and `ssh.import.preview` already answers any caller that holds the daemon token. A
  risk rule that makes the two reads match is left to a later slice.
- The verbs that write (`save`, `remove`, `hostkey confirm|forget`, `import apply`) follow in their own slice, with
  a security review.

### The ssh connecting reads (issue #3537, slice 2)

`ssh hostkey check <target>` and `ssh test <target>`, over `ssh.hostkey.check` and `ssh.test`. Both make the daemon
connect to the destination (`ssh-keyscan`, or `ssh -o BatchMode=yes`), and neither changes a destination or pins a key. The
daemon still does what these commands always did: `check` opens the five-minute window in which a confirm that quotes
the fingerprint pins it, and `test` writes the content-hashed `kh-*` and `config-*` files of its own directory,
built from the existing pins only.

- A target is its id or its name. The CLI reads `ssh.list`, an id wins, and a name that two targets share is refused
  with their ids. The resolver is `ssh/domain/target-ref.ts`, the same rule as the session reference.
- The request holds the target id and nothing else. A `vault-key` target is refused in the terminal, before
  anything connects: its key is delivered by the app over a near connection, and a terminal never sends one. A
  `password` target reaches the daemon, which answers `ok: false` (no askpass without the app).
- Exit 0 only when the answer is good: a pinned key that matches, or a login that works. `hostkey check` exits 1 for
  a key that is not pinned yet (`host_key_unknown`) and for a key that changed (`host_key_changed`), as
  `ssh-keygen -F` exits non-zero for a host it cannot vouch for; the status is in the output and in `--json`, which
  prints the daemon's check as it is. A failed `test` exits 1 with the daemon's words, and `--json` keeps its
  `reason` and `params`.
- These verbs wait up to 60 s, not 15 s: `ssh-keyscan` allows 5 s and each hop of a jump chain 10 s. A run that gets
  no answer is exit 2 and says nothing of a change, because the CLI changes no destination.
- The transport guard of the ssh commands is still not part of this slice.

### The ssh host key writes (issue #3537, slice 3a)

`ssh hostkey confirm <target> --fingerprint <SHA256:...>` and `ssh hostkey forget <target>`, over
`ssh.hostkey.confirm` and `ssh.hostkey.forget`. They change which server keys a host trusts.

- The fingerprint comes from the person's argv and from nowhere else. `confirm` first runs `ssh.hostkey.check`, which
  re-arms the daemon's five minutes and shows what the server presents now, and sends `ssh.hostkey.confirm` only when
  the typed fingerprint equals that one. It sends what was typed, never what the check returned, so a key that changed
  between the person's look and the call pins nothing (`ssh_hostkey_mismatch`, exit 1, nothing sent). The daemon still
  refuses a confirm with no pending scan, an old one or another fingerprint.
- A key that is already pinned (`ssh_hostkey_exists`) or that changed (`host_key_changed`) is exit 1 with nothing sent.
  `confirm` never forgets and then pins: replacing a key is two commands the person types, `forget` and then
  `confirm`, and the message says so.
- `forget` takes the destination and nothing else; it also drops a pending scan. `--json` prints the destination as
  the daemon returns it for both verbs.
- The risk rules rate `ssh hostkey confirm` and `ssh hostkey forget` high from a session's shell, through `fd`,
  `flightdeckd`, `bun run .../bin.ts`, `bash -c`, quoted or split words, and options before the noun. The three words
  are matched together, so `ssh hostkey check`, `ssh test`, `ssh list` and a sentence that names the verb stay ordinary.
  `--fingerprint` joined the options-with-a-value list the rules skip (the card rules had a bypass through it).
  `--fingerprint` is only a word the caller types, so the rating is the gate, as for `--confirm`.
- No device proof applies: `PROOF_COMMANDS` (#3453) has no `ssh.*` entry, so the daemon asks for none. Adding one is a
  protocol change and is not part of this slice.
- The transport guard of the ssh commands is still not part of this slice.

## Reading a project from a shell (issue #3515)

Slice 1 of the `project` noun: `project trust-state`, `project stack`, `project trust-inspect` and
`project harness-preview`, over `project.trust.state`, `project.harness.stack`, `project.trust.inspect` and
`project.harness.preview`. The write side (`detect-provider`, `add`, `update`, `harness-draft`, `harness-export`) is the
second slice. `harness-apply`, `harness-commit` and `trust-set` stay without a command for now; `trust.set` already takes
the device proof (#3453), and a verb will reuse that gate and add no second path.

- The handlers already resolve every folder with `resolveAllowedCwd`, so a folder outside the allowed roots is
  refused with `forbidden_cwd` and no new check was needed; the verbs only pass the folder on.
- A folder is made absolute against the shell's folder before it is sent (the daemon's own folder is another one);
  with `--host` it must already be absolute, because it is read on that host.
- `trust-inspect` (and `harness-preview` with `--template`) are near-connection only on the daemon, because they show
  commands and server arguments whole, a secret in one included. A `--host` call is refused there with the daemon's
  own reason; the CLI adds no exception. They read the project's own files, which a session in that folder can already
  read, so the verbs get no risk rating in this slice.
- `stack` reads the project's manifests and prints the commands it would use; it runs none of them.
- `--parts` is a comma list of the protocol's parts, each once; `--template` is a template id.
- Output: lines for a person, the daemon's answer whole under `--json`. A part of the answer that was cut for size is
  said (`left out of the lists`), not dropped.
