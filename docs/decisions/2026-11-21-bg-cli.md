# Background sessions from a shell (issue #3734)

One noun in [the CLI-first decision](2026-11-19-cli-first.md): `bg list`, over `bg.list` (slice 1), and the write side,
`bg start`, `bg stop`, `bg respawn` and `bg message`, over `bg.start`, `bg.stop`, `bg.respawn` and `bg.message`
(slice 2, below).

- The noun is `bg`, the word the protocol uses (`bg.list`, `bg.start`, ...), not `background`.
- `bg list` prints a head line with the count and one line for each session: id, state, status, what it waits for,
  the name (the folder when it has none) and the cost. A host whose `claude` has no background sessions says so and
  exits 0, with `supported: false` and an empty list under `--json`: it is a fact about the host, not a refusal.
- `--json` names the fields of a session one by one, so a field the daemon gains later does not appear in a script's
  input without a decision here.
- The handlers of these commands do not call `requireVaultTransport`; whether a command on another host's background
  sessions needs it is the transport guard of #3439 and is not decided here.

## The write verbs (slice 2)

- What the daemon already checks stays with the daemon: `bg start` takes only a folder under its allowed roots, runs an
  untrusted folder without the project's hooks and servers, and refuses an unknown card or a host with the feature
  off; `bg respawn` refuses an untrusted folder and a worktree; `bg message` refuses a running session that has no
  channel. The CLI adds no second check of these and prints the daemon's reason with exit 1. It refuses before it
  connects only what the request schema would refuse: an id that is not an id, an empty or too long text, a start with
  neither a card nor a folder and a prompt (or with both), a name over 120 characters and a persona that is not an id.
- The flags are the ones `session create` already has (`--cwd`, `--prompt`, `--name`, `--persona`) and `--text` of
  `snippet save`, plus `--card`, which only `bg start` takes. They are shared with other commands, so `takeBgFlags`
  moves them out of the shared fields once the line is read, as `takeSessionFlags` does, and each verb refuses the
  flags it does not take.
- Risk: the four writes are high from a shell and `bg list` is not. The issue proposed rating only `start` and
  `message` as high and leaving `stop` and `respawn` ordinary; all four are high here. `bg message` can resume a
  stopped session with any text, which is `bg start` by another route (`send` into a live session stays ordinary), and
  `bg stop` and `bg respawn` end or replace a session that may be mid-work. The rule sees only the command line, so it
  cannot tell a stopped session from a running one. No `--confirm` is added: a typed flag proves nothing, as for
  `rewind` and `agentcfg write`.
- A write waits 60 s, not the 15 s of the reads: the daemon waits up to 20 s for `claude` to start or resume, and a
  shorter wait would report a command that worked as lost. A lost answer is exit 2 with a hint to run `bg list` first.
