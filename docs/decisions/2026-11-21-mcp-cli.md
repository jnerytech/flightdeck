# The MCP servers of a project from a shell (issue #3616)

Slice 1 of the `mcp` noun in [the CLI-first decision](2026-11-19-cli-first.md).

`mcp list <project>`, `mcp status <session>` and `mcp test <project> <server>`, over `mcp.list`, `mcp.status` and
`mcp.test` without `confirm`. They read what the daemon keeps (or, for `test`, the command it would run) and change or
start nothing. The write side (`test --confirm`, `save`, `remove`, `toggle`) is the second slice, with its high-risk
rules.

- `mcp` was already a command: the stdio server that Claude Code launches. It stays one. A verb is a word right after
  `mcp`; a flag is never one, so `mcp --config <file>` is the server and `mcp list` is the read. A bare `mcp` with
  `--json` or `--host` is refused, since the server has no use for them. A test pins both.
- `list` and `test` take a project (its name or its id, through `resolveProject`); `status` takes the session id and
  hands it to the daemon as it is, so an unknown session is the daemon's own refusal (exit `1`). `test` never sends
  `confirm`: a daemon that answered with a started server instead of a preview would be refused as an unexpected
  answer.
- The text names the environment variables and headers of a server, never their values; `--json` carries what the
  daemon sends, which already masks both. The daemon does not mask `args`, so a secret passed as an argument shows in
  both outputs; the manual says to put it in a variable.
- `--json` keeps every key: `null` for the `type`, `command`, `args`, `env`, `url` and `headers` a server has none of,
  and for a status without an `error`.
- `mcp` joined the commands that take `--host` and `--json` (for its verbs). The risk rules need no new entry: nothing
  here writes.
